# M7 decision probe -- and it found something much bigger than the prefill gap
# box GPU0, qwen3-4b IQ4_KT, 22,000-token prompt + 256-token decode, -c 40960 -b/-ub 512,
# tip ds4-ports cb3246f9, 2026-08-04 08:0x
#
#            prefill_ms   prefill tok/s   decode ms/tok   decode tok/s
#   static      2,462         8,937           7.78          128.5
#   paged      43,600             -         220.70            4.5
#
# ★★ THE PAGED PATH IS ~18x SLOWER TO PREFILL **AND ~28x SLOWER TO DECODE** AT 22K CONTEXT.
# 4.5 tok/s for a 4B model on a Blackwell card is absurd on its face (accepted-absurdity
# rule): every prior paged measurement in this lane was at <=8K context with small pools,
# where the constant factors hide. The kernel's shape is the cause and it hits BOTH phases:
#   - one CUDA block per (head, seq, query token), head_dim (=128) threads per block;
#   - each block walks the ENTIRE visible context serially, one KV token at a time;
#   - so a decode step at 22K context = 22K serial iterations on 128 threads, with no
#     KV-axis parallelism (no split-K / flash-decoding) and no data reuse.
# Static banded FA parallelises over the KV axis and reuses tiles, hence 28x.
#
# ⚠ OPERATIONAL CONSEQUENCE (record it before anyone serves on this): --kv-paged is
# correct at long context but NOT fast -- it is a scheduling/memory win today, not a
# throughput win. Do not put a long-context production serve on the paged path until the
# kernel work below lands. Everything P2-8 proved (admission, preemption, sharing) STANDS;
# this is the kernel underneath it.
#
# ★ M7 SCOPE CORRECTED: it is not "tiled prefill", it is "the paged attention kernel needs
# KV-axis parallelism + tiling in BOTH phases":
#   1. decode: split the context across warps/blocks (flash-decoding), combine partials by
#      log-sum-exp -- the same shape the current kernel already uses ACROSS warps, extended
#      to a grid split so long contexts get real parallelism.
#   2. prefill: two-level (Q_TILE x KV_TILE) tiling per DESIGN-M7-TILED-PAGED-PREFILL.md.
#   3. or option B from that doc (gather + delegate to the already-gated banded FA kernel),
#      which now looks stronger: it fixes BOTH phases at once by reusing a kernel that is
#      already fast and already correctness-gated on both backends.
# Decision rule from the design doc is ANSWERED: prefill share is 55% (static) / 44%
# (paged) at this working point -- prefill matters, and decode matters just as much.

# == M7 PHASE 2 (tiled prefill, ds4-ports 4cb656dd, DS4P_PAGED_QTILE=1): 1.40x -- GATE NOT MET ==
#   prefill_ms 43,726 -> 31,272   (static reference 2,488)
#   test-paged-kv ALL PASSED; test-paged-banded ALL PASSED **with QTILE=1** (equivalence holds)
#   gate wanted >=5x. Flag STAYS OFF by default.
# ★ WHY (root, from the kernel I wrote): Q_TILE=8 cuts KV *loads* 8x but my mapping does
#   EIGHT separate warp-shuffle reductions per KV token (one per query in the tile) where
#   the old kernel did one. Loads went down 8x, reduction work went UP 8x -- net 1.4x means
#   loads were only part of the cost and the per-pair reduction is now the bottleneck.
# ★ THE FIX (next increment, this is what real FA does): stop reducing per (query, key)
#   pair. Map lanes to a Q_TILE x KV_TILE SCORE BLOCK -- each lane owns one (query, key)
#   product chain over a dim slice, so a warp computes 32 scores at once instead of one;
#   accumulate V into per-query registers from the score block. That is the MMA-shaped
#   inner loop; the outer structure (tiles, band, online softmax, cross-warp merge) is
#   already written and equivalence-gated, so the change is local to the score loop.
# Honest position: phase 2 as written is a correct but modestly-profitable step; it stays
# dark until the score-block mapping lands and the >=5x gate is actually met.

# == M7 PHASE 2b (score block) -- REGRESSED 3.4x, REVERTED (ds4-ports 2f9c4c81) ==
#   22K prefill: 31,272 ms (phase 2 tiled) -> 106,201 ms (score block) = 0.41x
#   test-paged-banded still ALL PASSED -> the MATH was right, the MEMORY SHAPE was wrong.
# ★ WHY: "lane owns a whole query's dot product" removes the shuffles but destroys
#   COALESCING -- each active lane then streams all head_dim values of the SAME k vector
#   from global memory by itself, so the warp re-reads one cache line q_cnt times instead
#   of loading it cooperatively (32 lanes x 4 dims) once.
# ★ LESSON (worth more than the commit): shuffles were not the whole cost. A mapping that
#   deletes them by breaking coalescing loses more than it saves. The win must keep
#   lane-owns-dims cooperative loads AND amortize each load across queries -- i.e. phase 2's
#   shape (4cb656dd, 1.40x) is the right skeleton and needs a cheaper per-query reduction
#   inside it (e.g. score several queries per shuffle tree, or stage K in smem once per
#   tile so the reduction reads smem instead of re-reading global).
# STATE: reverted to phase 2's mapping; DS4P_PAGED_QTILE still dark; M7 prefill OPEN with
# the search space now measured from both sides (too few reductions AND too little
# coalescing both lose).

# == M7 PREFILL: THREE MAPPINGS MEASURED, SHAPE'S CEILING FOUND (final, tip 52a58345) ==
#   22K prefill_ms      mapping
#   43,726              baseline (one block per query, no tiling)
#   31,272   1.40x      phase 2: Q_TILE=8, lane-owns-dims loads + per-query shuffle reduce
#  106,201   0.41x      phase 2b: lane-owns-a-whole-query (no shuffles) -- COALESCING LOST
#  218,100   0.20x      Q_TILE=16 -- REGISTER SPILL (16 queries x 4 acc + m/l per lane)
#   (static banded-FA reference: 2,488-2,542 ms; the >=5x gate needs <= ~8,745 ms)
# ★ CONCLUSION, measured from three directions: this kernel family's binding constraint is
#   REGISTER PRESSURE, not KV traffic. Q_TILE=8 is its local optimum at 1.40x, and the
#   >=5x gate is NOT reachable by tuning this shape -- bigger tiles spill, and removing the
#   reductions costs more coalescing than it saves.
# ★ THE ROUTE THAT REMAINS: an MMA / tensor-core inner loop -- score tiles held in warp
#   fragments instead of per-lane accumulator arrays, which is exactly how flash-attention
#   escapes this ceiling (and why the static banded kernel is 12-18x faster here). That is
#   a different class of work: new kernel, fragment layouts, a correctness gate of its own.
#   Until it lands, DS4P_PAGED_QTILE stays DARK and paged prefill keeps the baseline path.

# == M7 STAGE 3b: WMMA FRAGMENT PREFILL, WIRED AND MEASURED (ds4-ports 07113d21) ==
#   22K prefill: 87,793 ms  (baseline 43,726 · best f32 tile 28,816 · static ~2,500)
#   = 3.0x SLOWER than the f32 tile path. Gate (<= 8,745) not approached.
#   test-paged-banded ALL PASSED under DS4P_PAGED_QTILE=2 -> the FRAGMENT MATH IS RIGHT.
# ★ ROOT: the shape, not the tensor cores. One warp owns a 16-query tile (32 threads per
#   block), so the SM sits nearly empty, and the per-row online softmax -- 16 rows x
#   head_dim scalar rescales per key tile -- serialises across that single warp. The
#   matmuls are fast; everything around them is 32 threads wide.
# ★ NEXT SHAPE (not a new idea, the same kernel with more warps): multiple warps per block
#   -- one per key tile or per row group -- so staging, softmax and the fragment ops
#   overlap instead of queueing behind 32 threads. That is the difference between "uses
#   tensor cores" and "is a flash-attention kernel".
# STATE: DS4P_PAGED_QTILE unset/=1 untouched and still the measured paths; =2 is the dark
